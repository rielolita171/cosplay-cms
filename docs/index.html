Step 1 of 3 — What it is

A self-hosted inventory for a cosplay collection

Cosplay CMS is a small content system that keeps track of a cosplay wardrobe. One record per costume, with the props that go with it, the contact lenses opened for it, the photos of it, the milestones it has passed and the maker who built the hard part. It is one Express server over one SQLite file, served from one HTML file — you can read the whole codebase in an afternoon.

Three ways to run it, one codebase

  • Node on 4001. npm install && npm start, or docker compose up -d — the same server, a different way of owning the process and the data directory.
  • Docker. The compose file binds the port to loopback, so the container is invisible to your LAN and you tunnel in.
  • Electron desktop on 127.0.0.1:4101. The same Express app required from a main process, packaged as a Windows installer — no second backend to maintain, and no port for anything else to reach.

Seven tabs

  • Dashboard, Costumes, Props & Accessories, Contact lenses, Wishlist, Maker Corner, Reference Lists
  • Wishlist is a filtered view of the costume rows, not a separate table, so an item is never in two places at once
No login, no build step and no CDN are three decisions, not three omissions. It is a single-user box you run yourself, so the boundary is your network rather than a session cookie; the frontend is one public/index.html with an inline stylesheet and one inline script, so there is nothing to compile; and nothing is fetched from anywhere, so the app still works on a machine with no internet. What that costs you — and the one exception, the desktop build's per-launch token — is stated in the desktop section and step 3.

Step 2 of 3 — Why it was needed

The tools all fit a warehouse

Cosplay collections grow sideways — one outfit, then the accessories that go with it, then the lenses for the convention, then a commission. None of that is a stock problem, and that is exactly why the obvious answers all fit badly.

Where the idea came from. One personal cosplay collection that ran out of spreadsheet. The specific failures, not the vague ones: an item lent to a friend was never written down, so it was still marked as owned for the whole convention weekend; money already spent on a build was not recorded anywhere, so "what did this cost me" could only be guessed at from receipts; lenses sat in a drawer until one was worn past its date without anyone noticing; and photos of a finished piece lived in three different phone galleries, searchable only by date. None of those are big enough to buy software for. All four together are the whole specification.
📊

A spreadsheet can't

Ask it "which of my lenses expire this month?" or "what's still out on loan?" and you are building a formula, not using a tool. It cannot hold a photo per record, and it stops being portable the moment anyone else touches it.

📦

An inventory app assumes a warehouse

Stock counts, reorder thresholds, purchase orders. A costume collection has none of those. It has condition, storage location, whether you still own it and whether the thing you made for it is in the box.

📷

Photos are the real memory

Six months on, which outfit had the detachable sleeve? Only a photo answers that — and photos live in a phone gallery where nothing can search them, sort them or tell you which one belongs to which character.

⏳

Lenses expire quietly

Consumables with a hard date, invisible in a cupboard, and wearing one past it is a real problem. A spreadsheet is never going to notice on its own — this one does, and tells you.

So the answer was to build the thing. One record per costume, props linked to it, lenses tracked per vial with expiry alerts, photos on everything, and a maker directory for the day a prop breaks.

Step 3 of 3 — How we solve it

Built for a real wardrobe, not a demo

Every feature exists because a cosplayer with a growing collection actually needed it — status tracking, loan records, photo milestones, expiry alerts, and a maker directory to call when a prop breaks.

👘

Costume catalogue

Fandom, character, brand, size, full-set flag, buy and sell prices, notes and reference links. Status moves a record between In Possession, On Loan, To Be Sold and Wishlist — and the Wishlist is just a filtered view of the same rows, so nothing is ever duplicated.

⚔️

Props & weapons

Category, condition, storage location and notes, optionally linked to the costume it belongs to — so the Astesia sword shows up on the Astesia card.

👁️

Contact lenses & expiry

Per-vial tracking with unopened, active, expiring-soon, expired and disposed states. A scheduled checker pushes expiry warnings to Telegram so a vial is never worn a month past its date.

🛠️

Maker corner

The people who built your props: name, type — prop, weapon or accessory — and contact links. Each card carries real tel: and mailto: buttons, so reaching a maker is one tap rather than a note in a phone.

🏷️

Reference lists

Brands and fandoms as first-class, searchable tables with store links, not free text sprinkled through a notes field. Duplicate detection is near-string, so “1/3 Delusion” and “1/3 delusion ” are caught rather than both saved.

📸

Photos & milestones

Multi-image galleries per record, processed and re-encoded by sharp and renamed to opaque UUIDs, with a progress bar and percentage while uploading. A photo you pick shows up in the dialog straight away, and if you change your mind the file is deleted rather than left behind. Five independent milestone checkboxes — Costume Ready, Fullset, Costest Done, Event Done and Photoshoot Done — each worth 20%.

📦

Move it in one file

Export the whole collection — every record and every photo — to a single .zip, and import it on the other machine. Built for moving between the desktop app and a self-hosted server without hand-copying a database next to a folder of images. The import shows you what is inside, asks you to confirm, and backs up the current database first.

The operational reality, stated plainly. The whole collection is one SQLite file in a data/ directory next to an uploads/ folder; back it up by copying that directory, or move it by exporting the single .zip. There is no login, and that is a decision rather than an omission: it is a single-user box you run yourself, so the boundary is the network — trusted LAN, a tunnel, or an authenticating reverse proxy — and the port should not be published to the internet. The one exception is the desktop build, which mints a 256-bit token every launch and hands it to its own window and to nothing else; GET / and /health stay open there by design. Full detail on the desktop section.
Milestone percentages are not backfilled, on purpose. Completion is the plain count of ticked flags over five, and no flag implies any other one. Rows that predate the fifth checkbox therefore read 80% rather than being rewritten to a number that was never recorded — a wrong-but-tidy percentage is harder to notice than an obviously stale one.

Desktop app

Same server, now with a window

The desktop build is not a rewrite. It is the identical Express server, required from an Electron main process that supplies the four things Docker was providing: writable paths, the database bootstrap, a bundled sqlite3 binary, and a loopback-only port. One codebase, two ways to run it.

Known rough edges

  • Unsigned installer. Windows SmartScreen shows an unknown publisher warning until you click through, every time.
  • No auto-updater. New builds are a fresh download; the app will not tell you a newer one exists.
  • A desktop database is a different database. The app writes to its own userData directory — it does not read the one in your Docker volume or checkout. Move data with the export/import button, not by copying files.
  • The published v1.0.0 installers shipped with the token guard off. The guard module was latched by require caching before the environment variable was set, so both installers ran without it. It is fixed in v1.1.0, which is still being prepared — so on v1.0.0 the CORS allowlist is the only layer actually in force, and the boundary is your network.
Moving between the two is one button. Settings → Move this collection exports everything to a .zip and imports it on the other machine, in either direction. The origin allowlist is the one thing that does not travel, because it describes the machine rather than the data: it is discarded when the destination is the desktop app, and the destination server keeps its own rules (with loopback added for itself) when it is a server. Nothing you configured is ever removed.
Only the app's own window can read your collection. Two independent layers, because either one alone leaves a gap. An origin allowlist decides which pages may call the server, and a secret generated when the app launches is required on every request that returns data.

The second layer is the one that matters most, and it exists because of a subtlety worth knowing: CORS never stopped a browser from typing in the URL. CORS governs requests made by a page, not the address bar, and a top-level navigation carries no Origin header at all. So a page alone would not have been enough — anyone on that machine could point a browser straight at http://127.0.0.1:4101. With both layers, a browser gets an empty window and nothing else. Both layers ship in v1.1.0; on the published v1.0.0 installer the token layer is not running — see the caveat above.

This protects the app, not your data, and it is desktop-only. It stops websites, the address bar, and other software on the machine. It does not stop whoever owns the computer — the database file is readable on disk, and no application-level lock can change that.

A Docker or npm start install gets none of this. It has no login either, so the boundary there is your network: keep it on a trusted LAN or VPN, bind it to 127.0.0.1 behind a tunnel, or put an authenticating reverse proxy in front. Do not publish the port to the internet.

Under the hood

Boring on purpose

There is no framework, no bundler, no transpiler and no CDN request. The frontend is one public/index.html with an inline stylesheet and one inline script. You clone it, run it, and it works — which means it still works in five years.

  • Node 22+, Express 5, sqlite3 via short-lived child processes
  • Validation and SQL escaping on every write — a bad request is a 400, never a half-written row
  • Rate limiting on /api, Helmet, CORS allowlist
  • sharp for image processing; multer for uploads
  • Dockerfile and compose file included; SQLite file and uploads live in data/
  • Same server also packages as an Electron desktop app — no separate backend to maintain

Quick start

Running in two commands

# clone and install
git clone https://github.com/rielolita171/cosplay-cms.git
cd cosplay-cms
npm install

# run — listens on PORT (default 4001)
npm start

# open http://localhost:4001
# build and start the stack
docker compose up -d --build

# compose binds the port to loopback:
#   127.0.0.1:${CMS_PORT:-4001}:4001
# so it is invisible to the LAN and
# you must tunnel in.

# open http://localhost:4001
# run the desktop app from a checkout
git clone https://github.com/rielolita171/cosplay-cms.git
cd cosplay-cms
npm install
npm run electron:dev
#   -> serves on 127.0.0.1:4101

# or build a Windows installer
npm run electron:dist:win
#   -> dist/Cosplay CMS Setup 1.1.0.exe
#      (the file name follows package.json)

# if ELECTRON_RUN_AS_NODE is set in your
# shell, unset it first
unset ELECTRON_RUN_AS_NODE
Configuration is read from .env at the repository root. The names that matter are PORT, NODE_ENV, DATABASE_PATH, API_KEY, CORS_ORIGIN and TELEGRAM_BOT_TOKEN. Keep their values in .env — never in a commit.
This build has no authentication. That is deliberate: it is a single-user box, and the boundary is the network, not the application. Keep the port on a trusted LAN or VPN, put an authenticating reverse proxy in front, or tunnel it — ssh -L 4001:127.0.0.1:4001 user@host. Do not publish the port to the internet.
